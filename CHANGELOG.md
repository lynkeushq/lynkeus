# Changelog

## Unreleased

- `init` says what git will show and what to commit. In a trial, `init` said the token was "kept out of git" (true, through `.lynkeus/.gitignore`), but `git status` then listed `.lynkeus/` as new, and the agent added `.lynkeus` to the root `.gitignore` before reverting it. The token line now comes with two more: `.lynkeus/.gitignore` keeps the token, runs, caches and route map out, so `.lynkeus/` showing as new is expected and nothing goes in the root `.gitignore`; and what to commit: `.lynkeus/.gitignore`, `lynkeus.config.json`, the cases folder and `.claude/skills/lynkeus` (plus snapshots, funnels and lint baselines once they exist).
- The `case_run` description no longer says that only the seed applies on an attached Simulator or emulator. In a trial it contradicted `run.json` (which lists `seed` under `launch.unsupported` there) and the determinism guide (the device keeps its own `Math.random`). It now says what the code does: none of the four launch facts reaches the app there, the seed still makes the cases' own `{{random.*}}` repeatable, and `os_language` sets the device's language.
- `case new` finds a start that leads to the screen, and offers what is on it. In a trial, `case new --to About` began on DemoShowroom, the screen the app happened to show, and said "No known way from DemoShowroom to About", while `map plan Welcome→About` knew `press #about-button`. With no `--from`, a start with no known way now gives way to `cases.start`, then the first declared screen, when the route map knows a way from there, and the draft's comment says which and why. When no case reaches the screen, the draft also lists, commented out, the testIDs its source writes, short texts runs saw on it (`.lynkeus/screens`), and the presses that lead on from it, instead of placeholders only.
- A press that matched a label by part says which element it pressed, and whole words win over part of a word. In a trial, `app.press: "Favorite"` pressed the `Only Show Favorites` switch, and nothing showed it until a later step failed. The agent now ranks a control whose label holds the text as whole words above one where it sits inside a word (`Favorites`). `press` answers `! pressed "Favorite" matched only part of "Only Show Favorites" (button #fav-toggle)…` when the label is not the text itself, and a case run lists it as a warning (⚠ under the case, `warnings` in `cases.jsonl`). The ranking needs the app's JavaScript reloaded with the new agent.
- `why` no longer gives one of Lynkeus's own probes as the last command that failed. In a trial it said `the last command that failed was memory: Unknown method memory`: the run asks a host for its memory between cases, and an app without that command answers so. The commands Lynkeus sends between steps (`memory`, `logs`, `analytics`, `networkBodies`, `events`, `traceContext`, `nativeValues`, `nativeMocks`, `still`, `screenshot`, `record`, `clock`) are left out.
- `why` explains a 2xx whose body the app could not use. In a trial, a feed mocked as 200 with `{"status":"error",…}` left the podcast list on its empty state, and `why` said only "Timed out". `why` now reads the app's console for the time the step ran (lines a `--out` run already took, and those the agent still holds), and when the target is missing after a 2xx and the app logged a warning or error, it names both: `GET /v1/api.json 200 (mocked) answered, and then the app logged "Error fetching episodes: bad-data": the body is likely not the shape the app reads…`. Without a console line, a mocked 2xx now gets the "the data came" reason too, with a note that its body is the case's own.
- `case run --out` keeps the app's console and each step's requests with bodies, as the evidence guide says, without `--screenshots` or `--video`. In a trial, `console.error("Error fetching episodes…")` appeared in neither `cases.jsonl` nor `report.html` on iOS or Android: the agent kept the lines, but the run asked for them (and for request bodies) only when it also kept frames or a film. Now any run with `--out` files them under the step that printed them, in `cases.jsonl` and in `report.html`.
- The flaky warning compares runs only with runs on the same target and of the same app. In a trial, the ledger mixed iOS, Android and headless-host runs under one `simulator` target, called a case flaky after an app change broke it (the case file unchanged), and counted CLI runs that never started because the driver's port was taken. Each outcome in the ledger now notes what ran the app (`ios`, `android`, `fastsim:ios`, `host:android`, from the app's hello) and a hash of the commit plus the working tree's diff (cases and `.lynkeus/` left out); only outcomes that share both are compared, and the warning names the target (`is flaky on ios`). A case whose app never attached is not recorded, and `Port … is already taken` does not count.
- `case coverage` and `case impact` no longer count a navigator as a screen. In a trial on an Ignite app, coverage reported 6 of 7 routes with `Demo`, the tab navigator, as the one left, and `case impact` listed it as "reached, and touched by no case". A route whose component file declares other routes is now a navigator: it is left out of both counts (coverage names it on a line of its own, `navigators` in `--json`), and never listed as untested; the screens inside it count as before.
- `case coverage`, `case impact` and `ci --affected` follow macros. In a trial, `showroom-demos` reached DemoShowroom only through `app.inDemo` → `app.wait DemoShowroom`, so without `.lynkeus/seen` (as on a CI checkout) `case impact` left it out of a branch that changed that screen. The routes a case names now include those its macros name, through macros that call macros and with the `{{param.*}}` the case passes filled in; every `do` block counts, whatever its `on`, `when` or `unless`.
- Headless steps cost what the app takes, not a device's fixed waits. A trial measured headless presses at about 520 ms and typing at 650 to 870 ms with nothing animating; its run folders show the 520 ms presses were the ones right after typing, and the new step phases put most of each step in fixed windows meant for a device: the agent waited 300 ms for the keyboard to slide away before a press with a field focused, 80 ms for the keyboard to attach and 25 ms per key when typing, and 40 ms between the two looks that tell a target has landed; the runner waited a quiet window (50 ms) to read a press's target twice alike, and another (100 ms) before typing into a field already listed. On a host that is not a device (hello `native: false`, the headless host) the agent no longer waits for a keyboard it does not have, yields one turn of the event loop per key instead of 25 ms (each key is committed inside `act()` before the host answers), and looks a frame apart (16 ms); the runner takes a press's target as still at its first read and types once the field is listed. Devices and FastSim keep every wait. On a small fixture app (`case run --host`, 14 steps): a press 170 ms to 85 ms, a press right after typing 550 ms to 130 ms, typing three letters 370 ms to 30 ms, the case 2.4 s to 0.8 s. What is left of a press is mostly the 50 ms quiet window after it (`settle`), kept: it is how the next step reads what the press caused.
- Each step says where its time went. A trial agent saw headless presses take about 520 ms and a device's `app.inDemo` 3 s, and could not tell why. Steps in the case's report and `cases.jsonl` now carry `phases`: their `ms` split into `marks`, `target`, `action`, `settle`, `wait`, `look` and `events`, timed where the runner already waits (no extra call to the app), a macro's steps summed under it (`RunStepPhase` and `RunStep.phases` in lynkeus-protocol). The run's console writes them after a step of 500 ms or more (`app.press #next (548ms: target 66 · action 420 · settle 62)`), and `report.html` shows them on hover over a step's time, written out beside a slow one.
- `app.nav` right after a state change that swaps a navigator's screens waits for a navigator that declares the route, and fails if none does. In a trial on an Ignite app, `app.call signIn` then `app.nav Welcome` passed while Metro logged `The action 'NAVIGATE' with payload {"name":"Welcome"} was not handled by any navigator`: the root stack still listed only `Login`, and the step passed because the app went to `Welcome` by itself. The agent's check from earlier in this release (no mounted navigator declares the name) would instead have failed that step at once, a render before the stack lists `Welcome`. The agent now waits up to 1.5 s for a mounted navigator to declare the name (`declares` on `NavigationAdapter`, optional for adapters of other routers), then navigates; when none does, the step fails with `No mounted navigator has a screen named Welcome (the root's: Login)`. Agent unit tests; the trial's app ran an agent from before the check, so not run against it.
- A target `app.wait` found is one `app.press` finds. In a trial on an Android emulator, `wait { target: "Button", scroll: true }` passed in 248 ms on a drawer list and the next `press "Button"` failed with `No element matches` after 3 s. Both match the same way (the agent's `pick`), but the wait returned as soon as the row crossed the window while the list was still coasting from its swipe, and the list carried it on and recycled it before the press looked. A scroll wait on a device now returns only once the list has stopped (120 ms without movement) after its own swipe. A press whose target leaves while it waits for it to hold still scrolls back to it once, and otherwise says so: `No element matches {…}: it was on screen 120 ms before, and left while the press waited for it to hold still (a list still coasting after a scroll, a view animating away)`. A target that matches only hidden elements says `: one is in the tree but not presented (a11y)` instead of reading as absent. Agent unit tests; not run on a device.
- Screenshots, films and `os` commands follow the device the attached app runs on. In a trial with the Android app attached and an iOS Simulator also booted, `case run --screenshots --video` took every frame and the film from the Simulator's home screen. The MCP server's connection had looked up the device once, for the iOS app that attached first, and kept it (and simctl) when the Android app took the port. The device is now looked up again whenever another app attaches (platform, app id, name), always of the platform the app said, and with several booted the one where the app has a process (`xcrun simctl spawn <udid> launchctl list`, `adb -s <serial> shell pidof <app id>`); `--device`, `LYNKEUS_DEVICE` and `device` decide between several that run it. With `--on ios,android` each lane looks up its own. Covered by unit tests with stand-in `adb` and `xcrun`; not run on a Simulator and emulator together.
- Where a case must pass is now the project's decision, declared once: `cases.targets` in `lynkeus.config.json`, a list of `headless`, `fastsim:ios`, `fastsim:android`, `ios` (the app on the iOS Simulator or an iPhone) and `android` (the app on the Android emulator or a phone). A case's own `targets:` frontmatter replaces it for that case (a device-only feature, say). In a trial, an agent told that a case is done "when it passes on every available target" built and ran iOS, Android and headless for every case, though the project only needed FastSim. `case run --on targets` (`on: "targets"` over MCP) runs each case on its declared targets and nowhere else; a declared target this machine cannot run on is named with why and the run ends `⚠ check incomplete` and fails, instead of passing it over. With nothing declared it refuses and asks for them. Plain `case run` still runs on the attached app.
- `--on` names FastSim per platform: `fastsim:ios` and `fastsim:android` each take that platform's installed kit and last bundle (and `ci.hosts.command` only when its bundle draws that platform). `all` is now `ios`, `android`, `fastsim:ios`, `fastsim:android` and `headless`; `fastsim` alone keeps meaning the last bundle, whichever platform. A target's run folder and flake ledger use `fastsim-ios`, as `:` is not safe in every file name.
- `status` shows the declared targets and whether each runs on this machine, or, with none, proposes a value: FastSim for each of the app's platforms when FastSim is installed here, else `headless` and the platforms the app builds for (its `ios` and `android` folders; both when it has neither). `init` writes that proposal when the config has none and says so; `case init` keeps it. The MCP instructions, the skill and `status`'s advice now say a case is done when one `case_run` with `on: targets` passes, and to ask the person which targets matter when the project declares none.
- `lynkeus ci` (and `ci --affected`) follows `cases.targets`: each picked case runs on its declared targets a job can start (headless, FastSim), one target after another, each in `<out>/<target>` when there are several, with each target's report linked in the summary. `ios` and `android` are listed as not run; a declared FastSim target the job cannot start fails it as an incomplete check. Without `cases.targets` the job runs as before.
- `map ci --cases` adds a job to the workflow that runs `lynkeus ci --affected` on each pull request, on the project's CI targets; for each FastSim platform it installs the kit and bundles the app first. It is opt-in: it needs a backend (`ci.backend`) and `LYNKEUS_TOKEN`, plus `LYNKEUS_CLOUD_KEY` for FastSim and `LYNKEUS_REPORTS_KEY` with `ci.push`, in the repository's secrets, and a comment-only workflow must keep working. Without the flag, when `cases.targets` has targets a job can run, `map ci` ends with one line saying what `--cases` would add and which secrets it needs. `map check`'s next step points at `case run --on targets`.

- `case run --on` takes `ios` and `android`, and runs the iOS Simulator's app and the Android emulator's app side by side. In a trial with both running, `--on simulator` meant whichever app had attached on port 8123, so a run could not cover both, and the two apps took the port from each other. Both apps still dial the same port (no rebuild: the port is compiled into the app, and the Android agent dials 10.0.2.2 before `adb reverse`'s localhost, so a second port would not reach it). The driver now hands each app to the connection that takes its platform, by what the app says when it attaches: servers in one process may share a port when each says which apps it takes (`accepts` in `AgentServerOptions` of `lynkeus-client`), and an app none takes is let go. `all` is now `ios`, `android`, `fastsim` and `headless`; `simulator`, `emulator` and `device` keep naming whichever device app is attached. Each platform's run keeps its own flake ledger (`.lynkeus/flakes.ios.json`), runs of one process on a port's two platforms do not refuse each other, and `ios` or `android` without a Simulator, emulator or phone of that platform up is said at once. Covered by unit tests with two apps on one real port; not run on a Simulator and emulator together yet.
- The native values notice no longer calls a method a constant. In a trial on FastSim, a run said `KeyboardController.setFocusTo read as true (a function), and was never called: a constant with a wrong value`, with a `nativeMocks` snippet that set it to `null`, which would have made `KeyboardController.setFocusTo("next")` throw. react-native-keyboard-controller only copies the method into its own object (`setFocusTo: KeyboardControllerNative.setFocusTo`), so nothing was wrong. `case run` now reads the TurboModule spec of each module with such reads, where codegen finds it (`codegenConfig.jsSrcsDir` in the app's and each package's `package.json`, TypeScript or Flow): a member the spec declares a method is not listed; a constant of its `getConstants()` is listed as one. A member no spec covers is listed as a constant read as true or a method only referenced, and the snippet says it is for a constant only.
- `app.nav` reaches screens inside nested navigators. In a trial on an Ignite app, `app.nav: { route: Demo, params: { screen: DemoPodcastList } }` opened the podcast list and then failed with `Timed out waiting for Demo (on DemoPodcastList)`, and `app.nav: DemoPodcastList` failed with `Timed out waiting for DemoPodcastList (on Welcome)`. The step now waits for the screen it lands on (the innermost `params.screen`), and a navigator's name counts as reached once the focused screen is inside it, in `app.wait` and `app.see: { route }` too (agent side; with an older agent the step checks the screen's path when the wait times out). `nav` with a nested screen's name goes through its parents, which it reads from the path a run last saw the screen at, else from the route graph (a navigator is the screen whose component declares the nested ones): `app.nav: DemoPodcastList` sends `navigate('Demo', { screen: 'DemoPodcastList' })`. When neither knows the screen and no mounted navigator declares it, the agent says so and how to name the parent, instead of React Navigation dropping the navigate. A wait that times out on a nested screen names its navigators (`on Demo > DemoPodcastList`).
- The Lynkeus skill: an Agent Skill shipped in the `lynkeus` package (`skill/lynkeus`: `SKILL.md` and six topics, `cases`, `targets`, `evidence`, `ci`, `determinism` and `troubleshooting`, about 22 KB in all) with what an agent needs to write, run and debug cases. `lynkeus init` installs it in `.claude/skills/lynkeus` and says so (`--no-skill` leaves it out); `lynkeus skill install` updates it to the CLI's version. Lynkeus records what it wrote in `.lynkeus-skill.json` and never overwrites a skill whose files changed since, or one it did not write (`--force` does). A client that loads skills keeps only the one-line description in context until a task needs a topic.
- `guide`, a core MCP tool (and `lynkeus guide [topic]`): one topic of the skill per call, the topics offered as an enum, for clients without skills. A positional with fixed values now reaches the MCP schema as an `enum`.
- The MCP server's instructions are cut from 8,268 to 3,548 characters, which a client reads again with every call: what Lynkeus is, `status` and `init`, the cheap way to write a case, `case_impact`, closing the devices you booted, native mocks as the person's call and FastSim refusals. FastSim setup, sharing a run, evidence, teardown and sections, long suites, launch facts and mocks moved to the guide topics. The core tool list grows by `guide` (31 to 32 tools, about 7,040 to 7,210 tokens).
- The agent says the app's own bundle id or application id in its hello (`appId`, an optional field of `HelloEvent`, read once from the native module). Bringing the app back to the front, `app.relaunch`, `launch` and a crawl's or smoke run's recovery no longer need `app` in `lynkeus.config.json` or `--app`; those still win when given, and the "needs app id" error only appears when neither exists. Needs the app rebuilt with the new native module.
- `case run --on` without an attached app answered `simulator not available` only after the 15 s attach timeout. With no booted Simulator and no `adb` device it now says `no Simulator or emulator is running` at once, and with one running it waits 3 s for the app unless `--launch`, `--attach-timeout`, `LYNKEUS_ATTACH_TIMEOUT_MS` or `attachTimeout` ask for longer.
- An `on:` block inside a macro was not expanded: `cases.macros: { "app.x": [{ "on": "headless", "do": [{ "app.press": "#a" }] }] }` sent the fixtures server a command named `0` (`0: no fixture 0`), and in a teardown the macro failed without a word. A `do` in a macro (and in `cases.interruptions`) now holds one step or a list, as in a case. A teardown step that fails, a mock rule no request matched (`mock rule GET /v1/feed.json never matched; GET /v1/api.json went to the network`) and a relaunch before the first step are now warnings in the case's result: a ⚠ line under the case in the answer, and `warnings` in `cases.jsonl` (a field added to `RunCase` in `lynkeus-protocol`).
- `app.relaunch` starts the app again as a fresh case finds it: on a Simulator or emulator the app is terminated and launched and the step waits for it to attach, a host the run started (`--host-command`) is started again, and any other host mounts the app again (`reset`); a host that cannot answers `unsupported`. Before the first step, a case on a Simulator or emulator whose app is covered by a view the app did not draw (iOS's Save Password prompt left by the case before, an alert left open) relaunches it and says so in a warning. In a trial, the Save Password prompt after a sign-in case failed the next cases and cost about six runs to work around with a teardown `exec`.
- A target written as a bare number (`app.press: 7`) failed with `Cannot use 'in' operator to search for 'target' in 7`; it is an index, as `"7"` was.
- `app.call` right after a launch failed with `✗ Unknown method signOut`, because the app had not registered its commands yet. Within 5 s of the app attaching, a command it has not registered is asked for again until it is there; an app that attached earlier, or a release bundle that never registers it, still answers at once.
- `app.see: { target: "…", contains: true }` finds a text inside a longer one (a sentence in a paragraph); a target that is a text matches an element's whole text, ignoring case and outer spaces. The case reference and the README `case init` writes say so.
- A bare capitalized word in `app.wait` (`app.wait: { target: "Card" }`) or `why Card` is read as a route, and the failure said only `Timed out waiting for Card`. When the app has no route of that name Lynkeus knows of (the route graph, the screens read so far) and the word, or one close to it, is on screen, the error and `why` now say it was read as a route and suggest quoting it (`'"Card"'`) or `route:Card`.
- `case run --dry-run` (`dry_run` over MCP) answered only `✅ case`. It now lists each case's steps as a run counts them, each macro opened into the steps it stands for (with the `{{param.*}}` the case passed filled in and its `on`, `when` and `unless` named), and marks a step that is not one.
- `case new` without `--from` or `cases.start` refused to draft. It now begins at the screen an attached app shows (in a session or over MCP), else at the first screen the navigator declares, and says which in a comment. The setup is one comment naming the fixtures the project's server describes, instead of each fixture's example and parameters, and none while the server is still the example `case init` wrote (`create_user`, `give_points`).
- The flaky warning counted earlier versions of a case and real breaks: after a day of writing cases, every case read as flaky. A case's history now also starts again when a macro its steps call changes in `lynkeus.config.json`, and a failure that reproduced (it failed again on its retry, or at the same step with the same error in another kept run) counts on neither side.
- `git.changed` in `run.json` dropped the first letter of the first file (`ynkeus.config.json`): the porcelain status was trimmed before its columns were read. A rename now names the new file.
- On an attached Simulator or emulator the seed applied only to the cases' `{{random.*}}`, while `run.json` implied the app's random values were seeded too. `seed` is now listed under `launch.unsupported` there, and the run's notice says the seed still makes `{{random.*}}` repeatable but not the app's `Math.random`.
- `case run --video` films on an iOS Simulator and an Android emulator or phone, not only on Lynkeus FastSim. In a trial, `--video` on the Simulator kept no film, and the agent recorded the screen by hand with `simctl`. When the app's host does not film and the app runs on a Simulator, emulator or phone, each case is now filmed by the OS. On iOS it uses `xcrun simctl io <udid> recordVideo`, stopped with SIGINT so the file is finished. On Android it uses `adb shell screenrecord` on the device, stopped there and pulled into the case's folder when the case ends. Each step's `videoS` counts from the recorder's first frame, so the report plays the film from a step. A run that starts its own hosts (`--host`, `--host-command`) never films whatever Simulator is booted. `screenrecord` stops by itself after 3 minutes, and the Simulator writes frames only when the screen changes, so its film ends at the last change. A recorder that does not start is left out without failing the case, and the warning names both tools. Checked against a booted iOS Simulator; the Android path is covered by tests only.
- A run can be read and shared without the reports service or FastSim. In a trial, an agent with no `LYNKEUS_REPORTS_KEY` wrote its own HTML builder to show what its run did. Every `case run --out <dir>` now ends by writing `report.html` beside `run.json` and says where: `report: <dir>/report.html (open it in a browser, offline)`. The page needs no network or account. It shows each case by its last attempt (with how earlier attempts ended) and its steps under their sections, each with the frame after it. A failed case says why (diagnosis, evidence, the screen at the failure). The film plays from a step at the press of a button. Each step lists its requests with bodies, its events, logs and backend spans. A filter shows passed or failed cases only. It reads only what lynkeus-protocol's run format describes, so it shows any engine's run and refuses a schema it does not know. Frames and films are linked by their paths in the folder, and never by a path that leads out of it. `lynkeus report html <dir>` (`report_html` over MCP) writes the page again, and `--embed` puts the frames and the film inside it for one file to send. `lynkeus ci`'s job summary points at it.
- `case impact`, `ci --affected`, `map check` and `map impact` no longer flag every case that passes through a screen when a diff only renames a testID. In a trial, renaming `next-screen-button` to `welcome-continue-button` on the welcome screen flagged every case that went through it, though only the cases pressing that button (directly or through a macro) broke. A changed file is now compared with the base after printing both without comments or formatting and with the values of `testID`, `nativeID`, `accessibilityLabel` and `aria-label` set aside (string literals or templates, as JSX props or object properties). When nothing else differs, the file reaches no screen through imports. A changed testID reaches the cases whose steps name it, old or new (`#id`, `#id[2]`, a `testId` field, or a macro the case calls, through macros that call macros; a template's `${…}` matches any text), and a changed label reaches the cases that name its text. A change of only comments or formatting reaches nothing. Any other change keeps the file's whole reach, and the other files of the diff reach their screens as before. Swapped testIDs count as changed. A runtime without the reader (only React Native has one) keeps every importer.
- `map ci` wrote a workflow that only worked on the machine that wrote it, and that disagreed with `case impact`. In a trial, it pinned `lynkeus@0.7.7-dev.20261127010441`, a build only that machine's registry had, and checked `--depth 2` while `case impact` and `ci --affected` look 4 imports away, so the PR comment and the affected-cases run could disagree. The workflow now runs the range the app depends on (`lynkeus`, else `lynkeus-agent` or `lynkeus-headless`, released together). With none, it runs `^` the CLI's release. A dev build or a local path (`file:`, `link:`, `workspace:`) becomes the release it leads to (`^0.7.7`), and the command says so. The depth defaults to 4 everywhere, from one constant.
- `lynkeus ci` warned on every run and stopped hosts nobody had left behind. It asked the default headless host for `--screenshots`, though that host draws nothing, so each run ended with `⚠ --screenshots kept no frame…`. It now asks for frames only when `ci.hosts.command` names the hosts (FastSim, say). Every normal run also ended with `▸ stopped 5 host(s) the run left running`: `case run` sent its kept hosts SIGTERM and exited before they had, so `lynkeus ci` found them still listed and alive. `case run` now waits for every host it started to exit (SIGKILL after 2 s), so the line shows only after a run that died or was killed.
- `status` names the process holding the driver's port. In a trial, a `lynkeus mcp` left by another project's session held port 8123, and `status` said only that the port was taken. It now runs `lsof` and `ps` and says: `✗ port 8123 is taken by pid 13646 (npm exec lynkeus@0.7.6 mcp): Lynkeus 0.7.6 for another project, /Users/me/old-app. It cannot drive this project's app (each project has its own token) and keeps this driver from listening: stop it (\`kill 13646\`), …`. For a Lynkeus CLI the line gives its release (from `lynkeus@x` in the command or the package its script belongs to) and the folder it serves (`--root`, else its working directory). It says when that is this same project, left by another session. When the process is not Lynkeus it says so, and when `lsof` cannot tell, it says that.
- An app holding another project's token was refused, but nobody said so. The same trial suspected that the new app had attached to the stale server, and asked whether two projects could drive each other's apps. They cannot, and 0.7.6 already refused it: the app and the driver each prove the project token to the other (an HMAC over fresh nonces), and each drops a peer whose proof is wrong. A new test covers it with a real proof made from another token. What was missing was the message. The driver now says `An app dialed in once with another token and was refused: it is another project's app (each project has its own .lynkeus/token), or its bundle carries an older token…` (error code `wrong-token`), and `status` shows that line instead of a generic one. The agent logs `lynkeus: the driver at ws://localhost:8123 does not hold this app's token…` once until a driver proves the token again, instead of redialing in silence. The agent's message needs the app's JavaScript reloaded.
- A row below the fold of a FlatList or SectionList could not be reached headless, and two messages about it disagreed. ## 0.7.5

- `app.appstate background` on a Simulator or emulator no longer drives the suspended app: the runner stops calling its agent while it is in the background, and `lynkeus os appstate` gives the agent 3 s before it falls back to simctl or adb. Coming back to the front took 60 s (each call waited for its 20 s timeout) and long enough for an app with an idle lock to ask for its PIN; it now takes about half a second.
- `on: has:<command>` (and a macro that branches on it, such as a project's `app.login`) is decided against the commands the app has now, asked once per connection, not only the ones its hello listed. An app that registers a command after it connects was treated as lacking it, so such a login took its fallback route. The case log says when `has:` reads false or when the app's commands differ from its hello.
- A case can end with `teardown`: steps that put back what it changed outside the app (a Simulator's enrolled face, a setting), run after its steps whether they passed, failed or were skipped. A teardown step that fails is logged as a warning and does not change the result or the step count; a run cut by a timeout never reaches it. A run's report and `--out` do not list teardown steps.
- `lynkeus clock --advance <ms>` (`app.clock: { advance: ms }` in a case) now runs the timers and intervals that fall due inside those milliseconds, as `jest.advanceTimersByTime` does, instead of only moving what `Date` answers: a 5 s `setTimeout` fires on `--advance 5000` and not on `--advance 4000`, with no waiting. Timers run in due order, each at its own due time (`Date` answers that instant in the callback), and promise work a callback sets off runs before the next timer. It answers `advancedMs` and `nextDueMs` on every host. A timer that keeps setting itself again stops the advance after 100,000 runs with an error that names the cause. With `--settle` the order is advance, then settle. The headless host keeps real timers for everything else (a countdown still ticks in real seconds) and records each one's due time to run it early; Lynkeus FastSim moves its virtual clock. A Simulator or emulator has no `clock` command, so a case step there stays `unsupported`; a host older than this change only moves `Date`, and the command fails saying so.
- Launch facts: `lynkeus case run` takes `--seed`, `--locale`, `--time-zone` and `--epoch` (or `launch.seed`, `launch.locale`, `launch.timeZone` and `launch.epoch` in `lynkeus.config.json`, or `LYNKEUS_SEED`, `LYNKEUS_LOCALE`, `LYNKEUS_TIME_ZONE` and `LYNKEUS_EPOCH`; a flag wins over the config, the config over the environment) and records them in `run.json` as `launch` (`RunManifest.launch`, `RunLaunch` in `lynkeus-protocol`; a field only added, the schema stays 1). A host the run starts (`--host`, `--host-command`) receives them in its environment (and `TZ`), and `--host-command` also fills `{seed}`, `{locale}`, `{time-zone}` and `{epoch}`. The headless host makes `Math.random` repeat from the same place at launch and after each case, answers `react-native-localize` with the locale and time zone, and starts `Date` at the epoch (`lynkeus clock --reset` returns to it). An app that is only attached (a Simulator or emulator) keeps its own zone and clock: the run prints which facts it could not pass on and lists them under `launch.unsupported`. A value that cannot be used (`--time-zone Mars/Olympus`) stops the run with exit code 2. `case_run` over MCP takes the same four.
- `lynkeus clock --settle` (`app.clock: { settle: true }` in a case, after any `--now`, `--advance` or `--reset`) runs everything pending to idle without letting time pass: microtasks, timers due at this instant and queued renders, but not work due later. It is a mode of the `clock` command, not a new one, and answers `settled` (false when something keeps re-arming itself, like a `requestAnimationFrame` loop), `inFlight` (the requests the app still waits for) and, on Lynkeus FastSim, `nextDueMs` and `advancedMs`. `idle` is the other way to wait: it lets time pass until the screen is quiet. The headless host, whose timers are real, takes a few event-loop turns and stops once the screen has not committed for three in a row; Lynkeus FastSim runs its pump with the virtual clock held. A Simulator or emulator has no `clock` command, so a case step there is `unsupported`; a host older than this option answers without `settled` and the command fails saying so. `lynkeus-agent` now exports `requestsInFlight`.
- Requests can be held and released on demand, for a loading state that has to stay on screen: `lynkeus mock 'GET /v3/accounts' --hold` (`app.mock: { route: "GET /v3/accounts", hold: true }` in a case) makes matching requests wait, as far as the app can tell still in flight, before any rule or the network sees them, and `lynkeus mock --release ['GET /v3/accounts']` (`app.mock: { release: true }`) lets them go on, oldest first, to a rule or the network. The gate stays for the next requests (`--times n` holds only the first n; `--sticky` keeps it across an app reset on the headless host). `--clear` and an app reset release whatever is held, so nothing hangs, and a request the app aborted while held is not sent. `--list` shows the gates and what is held, and for how long. It is a new action of `netmock` (`hold`, `release`), so it works on the headless host and, through the agent, on a Simulator or emulator; Lynkeus FastSim has its own half. A held request is not waited for: `idle`, a frame's `--settle` and `clock --settle` go on without it, since the point is to look at the loading state, and `requests` and `clock --settle` report it apart as `held`, outside `inFlight` (`lynkeus-agent` exports `requestsHeld`; the `requests` answer gains `held`). A host older than this answers `netmock: unknown action "hold"`.
- A run now says which native values the app read that its host could not answer. Lynkeus FastSim answers an unknown native property with a function (it reads as true) and headless with `undefined`; both hosts now record each such read once and answer a new `nativeValues` command with `{ module, property, platform, host, readAs, called }`. `lynkeus case run` prints the list after the run (what read as true or undefined, with a `nativeMocks` snippet to paste), the MCP answer carries it, and `run.json` keeps it as `nativeValues` (`RunNativeValue` in `lynkeus-protocol`). A FastSim function the app called is left out of the summary: only properties read and never called are listed.
- `cases.nativeMocks` can set native constants: `"Module.name": { "value": … }`, `{ "ios": …, "android": … }` per platform, or `{ "absent": true }` (or a list of platforms) for a property that platform's module does not have. The CLI hands them to the host in `LYNKEUS_NATIVE_VALUES` so they are in place before the app's first read, on Lynkeus FastSim (needs the matching build) and under `lynkeus headless start`. Headless's `installDefaultMocks` applies them to `NativeModules` and `TurboModuleRegistry`. A `set` during a case changes only what the app has not read yet. Methods that return a value synchronously are not covered.

## 0.7.0

- The agent and the driver prove they hold the project token to each other, and neither sends it any more. Before, the driver's first message carried `LYNKEUS_TOKEN` in the clear, so any local process listening on port 8123 read it, and any process that connected could pose as the driver. Now the driver sends a random nonce, the app answers `hello` with an HMAC of both nonces, and only a driver that checked that proof sends its own (`verified`); the app serves no request before it. The protocol is version 2 (`PROTOCOL_VERSION`, docs/PROTOCOL.md). The agent and the CLI of different releases no longer attach to each other when the app has a token: update `lynkeus-agent` and `lynkeus` together.
- A connection that has not yet proved the token no longer replaces the app that is attached: a local process that connected in a loop used to knock the real app off the driver. At most 8 connections may be proving the token at once, each for 5 s, a refused one is closed at once, and frames from an unproven peer are capped at 64 KiB (32 MiB for the app once proven).
- An app started with no `token` option no longer serves whoever connects: the agent stays off and logs why, as it already did for an empty token (the log line now says both: `the app passed a token and it is empty (or no token at all)`). `allowUnauthenticated: true` turns this off for an isolated test environment only. If the agent went quiet after the update, check that Metro starts with `LYNKEUS_TOKEN` set (`EXPO_PUBLIC_LYNKEUS_TOKEN` in Expo) and the `lynkeus-agent/babel` plugin is in `babel.config.js`.
- Secrets no longer show up in what a run keeps. A value is replaced with `…` in the app's request log and traces, console and error lines (with their stacks), analytics events and store changes when its name reads as a secret: `password`, `pwd`, `passphrase`, `pin`, `otp`, `token`, `secret`, `apiKey`, `accessToken`, `sessionId`, `authCode`, `seed`/`recovery` phrases, `cvv`, `iban` and similar, in any spelling (`access_token`, `accessToken`, `x-api-key`). Names that only contain such a word (`item`, `cache`, `sort`, `monkey`, `status code`) stay readable. It also covers what used to leak: values inside strings (a URL's query, JSON kept as text, `name=value` pairs), header lists written as name and value objects, `Authorization: Basic` and `Bearer` credentials, JWTs and `Bearer` tokens inside any string, credentials in a URL (`user:pass@host`), the value after a path word such as `token`, `key`, `code`, `otp`, `pin` or `session` in a URL's path (12 characters or more, or 4 to 8 digits for a code, `otp` or `pin`), and encoded names (`%3D`). A report that showed a value you need, such as a code a case types, now shows `…`; read it from the case's own steps or from the backend.
- Report uploads are stricter. `--push` and the `report` commands refuse a reports URL that is not HTTPS (loopback is allowed for a local service) or that embeds credentials, and they no longer follow a redirect, so a service that moved cannot send your key somewhere else. If a push now fails with "the reports service must use HTTPS outside loopback", fix `LYNKEUS_REPORTS_URL` to the address the service answers on directly.
- A run's files are read safely when a report is uploaded: a symlink or hard link inside the run folder that points outside it is refused (`file path escapes the run directory`) instead of its target being sent. Case ids can no longer name a path: an id with a slash or `..` (and one that starts with a dot) is written as a folder or file name inside `--out`, `--events` and `--seen` with the odd characters replaced by `_`. A funnel name must be letters, digits, dots, dashes and underscores, so `funnel check` and `funnel report` cannot read a JSON file outside `.lynkeus/funnels`.
- Large runs upload in parts that stay under the service's size limit: a case's frames go up in bundles of at most 64 MiB, and a frame too big for a bundle is sent on its own.
- The headless host's network fence checks every hop of a redirect against `networkHosts`: a request to an allowed host that redirected to another one reached it, because the underlying fetch followed the redirect without asking. A redirect to a host that is not allowed fails with "network to <host> is off", at most 5 redirects are followed, and the `authorization` and `cookie` headers are dropped when a redirect changes origin. The WebSocket fence refuses anything that is not `ws:` or `wss:` (a Unix socket path was let through) and follows no redirects. If an app now fails on a redirect, add the host it lands on to `networkHosts`.
- `lynkeus relay [--cloud <url>] [--backend <url>] [--prefix <path>] [--ttl <seconds>]` lets an app that runs away from your machine (a device in a cloud farm, a runner on another network) call a backend that listens only on loopback. It opens one outbound WebSocket to the reports service with `LYNKEUS_REPORTS_KEY` (or `LYNKEUS_CLOUD_KEY`), prints the URL to give the app as its API address, and forwards only `/api/mobile/` requests to `localhost`, `127.0.0.1` or `::1`; nothing listens for inbound connections. The session lasts 15 minutes unless `--ttl` says more (3600 at most). It needs a reports service that supports it. See the new guide "Backend relay".
- `wait` takes `--anyOf` (repeatable) to accept the first of several targets that is present, and `--enabled` to wait until the target is there and enabled, such as a form button that waits on its fields. `what` is optional when `--anyOf` is given, and `--gone` with `--anyOf` is refused with a message, because it is not clear which target should leave. In a case, `app.wait: { anyOf: [...] }` takes strings or `{ testId }` and `{ text, nth? }` objects; before, a target written as an object in that list was read as the text `[object Object]`. `waitFor` has an `enabled` parameter in the protocol.
- A wait that matches a request tolerates a trailing slash: `app.wait: { request: GET /api/items }` and an app that calls `/api/items/` now meet.
- `lynkeus screenshot <file>` works on a host that draws the app itself (fastsim): the host captures its own frame instead of asking `simctl`, which found no simulator there. It writes only inside the output folders the host allows. The headless host still renders nothing to capture.
- `why` and a failed case's reasons name the requests that were still in flight when a command gave up, with how long each had been open (`GET /api/mobile/v3/user/ (open 20.5 s)`), including ones that started before the command. A request that never comes back is now told from a slow screen. On a host with a virtual clock (fastsim) the age is left out.
- The agent waits for a control that is still becoming interactive. A pager's last page arriving or a sheet sliding in reads as disabled for a moment, and a native tree that changes while it is read can answer twice differently: `press` and `swipe` used to fail with "is not presented (inert)" on a loaded machine, and now keep looking until the settle deadline. On a host with a virtual clock the settle also lasts at least 30 looks, since its deadline ran out before the native side moved. The case runner waits for a swipe's target on the wall clock for the same reason.
- `swipe` with a target keeps the finger inside the target: the start moved to force the requested distance put it on the outer pager for small cards and swiped the wrong thing. It starts at the near edge, and the end is clipped at the window. On the headless host a swipe on an element with no gesture of its own drags the scroller under it, as on a device, instead of failing with "No GestureDetector near the element".
- Optional presses (`optional: true`) skip a one-time sheet that went away between the check and the press, instead of failing with "No element matches". A keypad key that moves less than a point (a native transform's jitter) counts as still, so a flow no longer waits on a key it can already press.
- On Android, `type` goes through the keyboard's input connection, so a controlled React input sees every character, and `clear` empties the whole field when the caret was in the middle of the text (the suffix used to stay). Frames, field texts and hit tests are read on the main thread, so a view hierarchy that changes mid-read no longer breaks the read, and an element whose header text sits above the window (a title centered in a taller header) is kept as an offscreen assertion target, so `app.see` finds it while gestures refuse it.
- `lynkeus fastsim install --platform ios|android` downloads fastsim, the simulator that draws the app on a Mac or Linux without Xcode's simulator or an emulator, for an organization whose plan includes it: it asks lynkeus.io with `LYNKEUS_CLOUD_KEY` which releases the organization may install, checks the archive's SHA-256 and unpacks the build for this machine and platform into `~/.cache/lynkeus/fastsim/<version>/<variant>/` (`LYNKEUS_FASTSIM_DIR` moves it). It installs `darwin-arm64-<platform>` on an Apple Silicon Mac and `linux-<arch>-<platform>` on Linux x64 or arm64, including inside WSL2 on Windows; Intel Macs have no build, and `--variant` overrides the machine's build. iOS matches the simulator pixel for pixel only on a Mac. Over MCP it is the `fastsim_install` tool. The package's README says how to start a host for the app.
- A driver call waits for the app to reattach, up to the call's timeout, instead of failing at once with "No app attached" while the app reloads. The agent also answers a request resent on a reconnect once, not twice: a press sent again while its first copy was still running was done two times.

## 0.6.0

- `lynkeus headless start` no longer runs out of memory in a long suite. Every `jest.fn()` an app's mocks are made of (the jest preset's native modules, AsyncStorage, the app's own) keeps the arguments and result of each call for a test to read; a host runs for hours and nothing reads them, so its heap grew some 20 MB per sign-in and screen in a large app and hit node's 4 GB limit after about 30 cases, failing the case it was in. The host clears those records every 10 s; the mocks keep their implementations and once-queues. Measured on that app with no backend, 40 sign-out-and-Home cycles: the heap grew 1 GB before, 40 MB now, and flat once react-query's 5-minute cache window fills.
- `lynkeus call memory` on the headless host reads the heap after a collection, with no `--expose-gc` (which `NODE_OPTIONS` refuses), and says where the heap stops (`heapLimitMb`): a runner can compare a reading with the next case's and with the limit.
- On a device, `app.mock` with `lost: true` sends the request and loses only its answer, as the hosts do: it failed the request without sending it, so the server never acted on it (a provider link the app thinks failed is still saved), and cases checking that ran differently on a phone.
- A failed case's reasons no longer blame the backend for an answer the case mocked: a step's `app.mock` of a 500 read as "the backend answered 500 … a server error, not the app", and sent people to reproduce with curl what the case itself had made. A request a mock answered (or lost) is marked `mocked` in the app's request log and trace, its line in the evidence says `(mocked)`, and the backend rules (5xx, 401, 403, 429) read only what the server answered. The agent marks what its own `netmock` answers; a layer below it (the headless host's network fence, a host's own netmock) marks its answers with the `x-lynkeus-mocked` header.
- `case run --host` starts the host again when it died during a case (out of memory, a crash) or its app stopped answering: the cases after it all failed with "No app attached" and never reached the app. The case that lost the host still fails, and its reasons now say how the host ended, with its last words and its log; a host started again writes a log of its own. Before each case the run also asks the host how full its heap is (one line in the log) and starts it again past `--host-heap` percent of its limit (60 unless told), so a case does not begin on a host about to run out.
- The headless host's real network hands the app a body that is not JSON as the app's own `SyntaxError`: Node's fetch parsed it in Node's realm, so `error instanceof SyntaxError` inside jest's sandbox was false, and an app that reads an empty 404 that way (a Rails `head :not_found`) retried the request and stayed on its loading state where a phone shows "not found".
- `--video` keeps the film of a host on another machine (fastsim in a Linux VM or on a server): it filmed there, at a path that was this machine's, and the report had no video. The host's `record { stop }` says how big the film is and `record { read }` hands it over a piece at a time.
- A case can say it runs alone: `exclusive: true` in its frontmatter. Under `case run --jobs` it waits for the cases in flight to end, no other case starts until it has ended, and its setup is never made ahead. Cases side by side share one backend, and one that changes what every case sees (a global feature flag, a setting for all users) broke the cases running beside it: a sign-in that should have been refused was let in while another case had the flag on. A case waiting to run alone goes before the cases asked for after it.
- A long run says where it is. `case run` writes `progress.ndjson` as it goes (in `--out`, else `.lynkeus/last-run.progress.ndjson`): the run with every case and how long each took when it last passed, each case as it starts and ends with its job and host, and each step with its place and the numbered section it is in (`# 3 A wrong PIN` in the case). `--progress json` writes the events to stdout too.
- In a terminal, a run keeps a status line under its output: cases done and failed, time spent and left, and what each job runs and in which section. The time left comes from the cases' past times, else from this run's. `--progress none` leaves it out.
- `lynkeus case status [dir]` reads where a run is, during or after it, from any terminal (`--json` for a program); a run whose process is gone without finishing says so. Over MCP it is the `case_status` tool, and `case_run` sends MCP progress notifications to a client that passes a progress token.
- With `--push`, the report is made when the run starts and fills case by case, so its address works from the first case; a send that fails is tried again at the end. A reports service from before this gets the whole run at the end, as it did.
- A report says which numbered section of the case each step is in: a run file's step carries `heading` (`3 A wrong PIN`) from the comment that opens the section (`# 3 A wrong PIN` in the case's steps), so a report can group a long case's steps the way the case does. A step before the first numbered comment, and every setup step, has none.
- Over MCP, `case_run` takes `video` and `traces`, which the server's instructions told a model to pass and the tool refused, and `jobs`, `ports`, `host_command` and `in_order`, so a client can run a suite side by side and `exclusive` cases mean something there. The instructions a client gets on connecting cover numbered sections, long suites (`case_status`, progress notifications) and mocked answers.
- `lynkeus requests` and `lynkeus trace` mark a request a mock answered `(mocked)`, as the evidence of a failed case does.
- The format `case init` writes explains numbered sections and `app.mock` (with `lost: true`), and its example case uses sections.
- An Android phone on USB works as an emulator does. The CLI runs `adb reverse` for each phone it finds when it starts listening, and an Android app with no `host` set tries the emulator's address (10.0.2.2) and then localhost until one answers, so a phone reaches the driver with no setup; its native log (logcat) is kept as an emulator's is. An iPhone is not supported yet: simctl drives only simulators.
- `case run --keep-hosts` with `--host-command` starts each job's host once and keeps it for the job's cases, starting it again before a case when it exited, its app stopped answering, or its heap is past `--host-heap` percent; `--host-timeout` is how long a host may take to attach. A case that failed because its host died says so.
- `lynkeus ci` runs its hosts that way, so a host that dies takes one case with it, not every case after it; it reads the first port from `LYNKEUS_PORT` or `port` in the config (8123 unless told) instead of always 8123. `--keep-up` now leaves the backend up; the hosts end with the run.
- `lynkeus mock --lost` refuses `--status`, `--body` and `--delay`: a lost request gets no answer to shape, and they were dropped without a word.

## 0.4.0

- `lynkeus headless init` installs what the Node host runs on (jest, `@testing-library/react-native`, `lynkeus-headless`) when the app lacks it, and is served over MCP. `headless start` says what is missing instead of failing inside `npx jest`, and when the app's jest configuration does not set them it passes the React Native preset and the `transformIgnorePatterns` that let React Native, React Navigation, Expo and the like through, so an app with no jest setup of its own runs headless as it is. `status` says whether the app can run headless. A package manager is found by the lockfile above the app too, as in a monorepo.
- `lynkeus mcp` can set a project up and test it, not only drive an app that is already attached. It serves `init` (which now also installs `lynkeus-agent`, with Expo's installer or the project's package manager), `status` (new: what the project has and, for each thing missing, what fixes it), `case init` and `case run`, and tells the model that connects the order to do things in. `LYNKEUS_REPORTS_URL` defaults to `https://lynkeus.io`, so pushing a run needs `LYNKEUS_REPORTS_KEY` alone. `init` adds the Babel plugin to a config written on one line.
- `lynkeus init` makes the project's token and nobody sets a variable for it: it writes a random one to `.lynkeus/token` (kept out of git by `.lynkeus/.gitignore`), and the CLI, `lynkeus mcp`, `lynkeus headless start` and `lynkeus-agent/babel` read it from there. An Expo app gets it as `EXPO_PUBLIC_LYNKEUS_TOKEN` in `.env.local`. `LYNKEUS_TOKEN` in the environment still wins, so nothing changes for a setup that sets it.
- `case run --video-scale <n>` asks the host for a film of that many pixels per point. fastsim films at 2 unless told, and takes 1 to 3: sharper costs time and bytes (one case took 34 s at 3, 22 s at 2 and 21 s at 1; 15 s with no film).
- `case run --screenshots` waits 150 ms of a still screen before each frame, where it waited 700 ms: the wait is paid on every step and was half the time of a filmed run (three cases at once took 133 s, and 68 s without it). `--settle <ms>` sets it; `--settle 700` gives the frames two runs can be compared by, pixel for pixel.
- Setting an app up over MCP, tried on a bare project and on a copy of a React Native app with Redux and styled-components: a failed install says why (the peer range that does not match) instead of where npm keeps its logs; `headless init` makes the project's token too, since `headless start` refuses to run without one and an app tested only headless never runs `init`; `apiUrl` in `lynkeus.config.json` gives the host its local backend when the environment does not, because an agent cannot export a variable; Redux Toolkit, React Redux, Redux, Reselect and Immer are let through jest's transform, as they ship ES modules to React Native; and `case run --host` reports the host's own explanation of a crash, where it cut it off at jest's code frame.
- An Expo Router app runs on the headless host. It has no root component, so `headless init` writes an entry that renders the router over the app's route files with `expo-router/testing-library` and mounts the agent with `auto()`, which then knows the routes. For an Expo app it installs `jest-expo` (with Expo's installer), and `headless start` gives Jest that preset, maps style sheets to an empty module and maps the `tsconfig.json` aliases, the longest first. On React Native 0.86 and later, which moved its Jest preset out of `react-native`, `headless init` installs `@react-native/jest-preset` of the same version. A new Expo SDK 57 app, set up and tested only over MCP, passes a case in under half a second.
- `headless doctor` is served over MCP (`headless_doctor`), so an agent setting up headless sees which native modules still need a mock, and the server's instructions give the headless order of things. It no longer counts a mock or a native module named only in a comment: the generated entry's example `jest.mock('some-native-package', …)` was listed as mocked.
- `lynkeus mcp` exits when its client closes the connection. It used to stay, holding the driver's port, and the next server or `case run` could not bind it.
- `lynkeus-headless` mocks `react-native-vector-icons`' native module, so a screen that renders an icon to an image (`getImageSourceSync`) loads in the Node host instead of failing to render.
- A failed `app.see` with its own `timeoutMs` takes about that long. On an app that says it is native, a text that was not on screen got a last look of 20 s whatever the step asked, so a step of 1.5 s failed after 22 s; the 20 s stay for a step that names no timeout.

## 0.3.0

- `lynkeus-agent`: a token that the app passes and that arrives empty keeps the agent off, with a line in the app's log saying why. It used to mean "no token", and the agent served any driver that connected. In a React Native app that was every app that followed the README, because `process.env.LYNKEUS_TOKEN` is undefined inside a bundle. **An app that passes `token` now needs the value to reach it**: `lynkeus-agent/babel`, a Babel plugin, writes `LYNKEUS_TOKEN` into a development bundle (never a release one), and `lynkeus init` adds it to `babel.config.js`. `auto()` with no `token` at all still serves without one.
- An app that says it runs on Android has its device found through `adb devices`. With an iOS simulator booted beside the emulator, the CLI took the simulator's id for it, and a screenshot, a launch or an `os` command went to `adb` with an id it did not know.
- `wait` and `see` take `route:<name>` for a route that does not start with a capital, as Expo Router's do (`route:index`): a lowercase word alone is still a text to look for.
- `lynkeus init` mounts the agent from the app's entry. In an Expo app it reads the token from `EXPO_PUBLIC_LYNKEUS_TOKEN`, the only kind of variable Expo passes to the app, and an Expo Router app, which has no entry of its own, gets an `index.js` that mounts the agent and then loads the router. Tried on a new Expo SDK 57 project: a development build attaches, lists the screen and names Expo Router's routes; no config plugin is needed.
- A target in quotes is the text inside them: `press '"Next"'` used to look for a label with the quotes in it and find nothing. Quoted, a word is never a route, an index or a testID, so `wait '"Next"'` waits for the button and not for a route called `Next`.
- Cases: `app.press` and any step that takes a `target` take `testId` in its place, `app.press` takes `{ text }`, and `app.type` takes `timeoutMs` for how long its field may take to arrive. Each was refused with `press has no testId`, `app.press needs a target` or `type has no timeoutMs`.
- `lynkeus lint --baseline` knows a finding again by its rule, its testId and what it is about, not by its message. The message carries what was measured, so a target that went from 32 to 30 points came back as new. A baseline saved before this still matches on the message it kept; save it again to get the new behavior.
- `qa.observe` works with a Redux store. It read the new state from the listener's argument, which Zustand passes and Redux does not, so every key of a Redux store was traced as changing to nothing. It now reads the state from the store.
- The store changes in the trace no longer carry a secret or a payload: a key named like one (`token`, `password`, `session`…) is traced as `…`, and a string longer than 80 characters is cut. A trace is part of what a report uploads.
- `lynkeus-agent`: importing the package no longer evaluates the client. `start`, `createHandlers` and `dispatch` were re-exported from the entry, so an app that imported `<Lynkeus>` and left it disabled, as a release build does, still evaluated everything that reads the screen unless Metro inlined its requires. They are now required when called.
- Docs: the protocol's handshake as it is (the driver's `auth` always comes first and carries a `session`; `hello` answers it), how the app paces its dials, the `trace` method, and what was unsaid about physical devices, film and Expo Router on the headless host. Node 22 is the oldest supported everywhere it is named.
- `lynkeus-agent`: an input's `value` is what its native field holds. It was read from React's props, so a field the app does not control (no `value` prop) read as empty after typing, and one with a `defaultValue` went on reading as that. The native module answers `texts(tags)`; an app has to be rebuilt to get it, and until then the agent reads the props as before.
- `lynkeus-agent` on Android: a control is covered only by what a touch would stop at. The agent's own search took any visible view over the point, and React Native lays an invisible debugging overlay over every dev build, so every control read `~covered` and a case waited out its deadline before each press. It now asks React Native's search for a touch's target. An app has to be rebuilt to get it.
- `lynkeus lint` measures the contrast of every text against what is behind it, on the pixels of a screenshot, and reports what falls short of WCAG 2 AA (4.5 to 1, or 3 to 1 for large text) as `low-contrast`. Elements say the size and weight of their text (`font`, optional in the protocol). `lint.contrast` in the config sets the ratios, leaves testIDs out or turns it off; `--no-contrast` skips it once. A host that takes no screenshots says so and reports the rest.
- `lynkeus-agent` on Android: an element is where its view stands, not where the shadow tree puts it. In an app that draws under the status bar the two were a status bar apart, so a press landed above its target. The native module answers `frames(tags)`; an app has to be rebuilt to get it, and until then the agent behaves as before.
- Cases: `on:` takes `has:<command>` (the app registered that command, as a hosted build often does and a store build does not) and `!` in front of any condition, so one case or macro carries the way each host does a thing. `app.press` waits half a second for a target that is not listed and then scrolls to it, instead of spending its whole deadline first, and waits for a disabled control through the app rather than by sleeping, which lets a host with its own clock move on.
- `case run` on a device, or a host that lists only its window: `app.see` and `app.press` scroll to what they look for, and `app.see` gives a missing target a short wait, a scroll and a long wait before its deadline counts. A case no longer needs a swipe written before each element below the fold.
- Fixtures: before the first case lynkeus sends `{"command": "lynkeus.describe"}` to the project's fixtures command. A server that answers `{"commands": [...]}` has its cases checked first, and one that names a fixture missing from the list is refused before anything runs. A server that answers `"ok": false` is left unchecked. `case init`'s server answers it.
- A case step the host cannot do (the app or host answers `Unknown method`) is reported as `unsupported` instead of failed. The case stops there with result `unsupported`, is not retried, and does not fail the run: `3/5 passed, 2 cannot run on this host`.
- `case run --out <dir>` writes the run as a directory: `run.json` (when, on what, totals) and `cases.jsonl` (a line per attempt, each step with its section, outcome and the analytics events it caused). `lynkeus-protocol` exports its types (`RunManifest`, `RunCase`, `RunStep`, `RunEvent`) and `RUN_SCHEMA`, the contract for whatever reads a run.

## 0.2.0

- `lynkeus`: commands regrouped. Static knowledge is `lynkeus map build|screens|show|paths|plan|impact|check|changes` (was `graph`, `screens`, `screen-info`, `paths`, `plan`, `impact`, `check`). What the OS hands the app is `lynkeus os deeplink|appstate|clock|biometrics|scan|gallery|permissions|push|appearance|location|language` (was the bare names and `lynkeus device …`). The host is `lynkeus headless start|init|doctor` (was `headless`, `init`, `doctor`). `lynkeus mock` is unchanged. The old spellings still work as aliases.
- New commands: `see` (assert a route or element is on screen now), `hello` (what the app said about itself), `screen --tree` (the screen as nested lines of meaning, no geometry), `snapshot <name>` (a tree baseline by default; `--pixels` adds the screenshot), `flake` (the same flow n times), `why` (why the last step failed, from the screen, requests and trace), `record` (a flow from what a person does in the app), `lint --save` / `--baseline` (only the findings that are new).
- `lynkeus.config.json` in the app's folder holds what was repeated as flags: `entry`, `apiEnv`, `port`, `device`, `app`, `attachTimeout`, `lintBaseline`. Flags win over the environment, the environment over the file.
- Global flags: `--root`, `--device`, `--app`, `--launch`, `--attach-timeout`, `--json`, `--help`.
- The token env var is `LYNKEUS_TOKEN`. `lynkeus headless start` refuses to run without one.
- Headless respects what a device would refuse: a swipe on an element the platform is not presenting fails; a swipe across a scroller scrolls it (a pager turns its page), and frames follow the scroll. Percentage widths and heights are laid out.
- `screen` lists only what is presented and counts the rest in the header (`--all` lists it), prints coordinates only with `--frames` and read stats only with `--verbose`; states read `!disabled`, `~covered`, `~inert`. About half the tokens per screen; an icon inside a button is not listed. Recorded screens keep only what is presented.
- `lynkeus mcp` serves nine core tools (about 750 tokens a turn, against 4,200 for all of them); `--full` serves all of them.
- Targets can be scoped: `press '#like' --in 'hi from Ana'`, `--nth 2` (protocol: optional `within`). `wait <target> --scroll` swipes until it is in the window; a device press brings an offscreen target in first. `type … --submit` sends the return key.
- Every app answers `events` (what `qa.event` recorded) and `stores` (the state of what `qa.observe` exposed). `run --events` keeps each step's events; `events`, `events diff`, `funnel check` and `funnel report` read them against `.lynkeus/funnels/`.
- `map check` and `map impact` follow a named import through a barrel to the file that defines it: a changed hook reaches the screens that use it, not every screen that imports from the barrel.
- `case run` runs cases written as markdown: `app.*` steps drive the app, any other step is a fixture answered by a command the project declares (JSON lines), `assert` reads the backend, and `cases.macros` names steps of the project's own. `case init` writes an example, the reference and a fixtures server to start from.
- `map ci` writes a workflow that comments on each pull request which screens its diff reaches.
- A command outside a session attaches in about 100 ms (it was 120 ms to 1.8 s): the agent redials every 100 ms for 3 s after a drop, the driver listens before asking the OS for simulators, and the source extractor loads only for `map build`. The crawl returns to where it began instead of a fixed route. `debug` names the component that blocks a touch.
- Linted with Biome in CI; `lynkeus-client` and the protocol's shapes are tested; no product names in the sources, and a test keeps it so.
- Docs split: the README is a landing page; the manual lives in `docs/` (CONCEPTS, DRIVE, HEADLESS, KNOWLEDGE, TROUBLESHOOTING) next to the generated COMMANDS and PROTOCOL.
