# Changelog

## Unreleased

- `cases.appEvents: { provider }` names the service the app's own event list feeds, so a report shows those events under it (Mixpanel) instead of "App". A run file keeps a backend event's origin as `server`, which a report marks.
- What the backend told its own analytics shows under each step too. `cases.serverEvents` names a fixture that, asked with the step's start, answers the events the backend sent since (an Olympus that hands Mixpanel events to background jobs reads them back from those jobs); a report lists them with the app's, under the service they went to.
- `case run --no-app-events` leaves the app's own event list unread while a run keeps a report. Reading it can turn on an app's tracking debug, which may draw on the screen; frames that two runs compare should not have it.
- Where the host records SDK calls (fastsim, the headless host), a run no longer asks the app for its event list as well.
- Events are recognized from the analytics services most apps use. By host, on every target: RudderStack and Customer.io (read as Segment batches), Google Analytics, Google Tag Manager, Meta, TikTok, Iterable, MoEngage, Kochava, Singular, Embrace, Instabug (Luciq), Smartlook, Airship, Snowplow, FullStory, mParticle, Pendo, LogRocket, New Relic, Hotjar and Countly, next to the ones before. By native module, in `lynkeus-headless`: Meta app events, Iterable, MoEngage, Kochava, Singular, Embrace, Instabug, Airship, Snowplow, FullStory, mParticle, Pendo, New Relic, Countly, Heap and PostHog.
- A report shows what each request sent and got. While a run keeps evidence (`--out`), the agent keeps each request's headers and body and its response's, with secrets replaced by `…` (passwords, codes, PINs, tokens, card numbers, `Authorization`, cookies) and bodies cut at 16 KB, and the runner files them under the step that sent them. It comes from the app, so it works on fastsim, a simulator, an emulator and headless, with or without backend traces. Outside a run the agent still keeps only method, address, status and time.
- Each analytics event says which service it went to. `lynkeus-headless` stands in for the native modules of Mixpanel, AppsFlyer, Intercom, Sentry, Datadog, Firebase Analytics and Crashlytics, Amplitude, Braze, Branch, Adjust, Bugsnag, CleverTap and OneSignal and records their calls per SDK, as fastsim does; and on any host, requests to Segment, Amplitude, PostHog, Mixpanel, Sentry, Datadog, Firebase, AppsFlyer, Branch, Braze, OneSignal, Intercom, Bugsnag, Adjust, CleverTap, Heap, Statsig and LaunchDarkly become the events their bodies carry.
- Report frames are AVIF where the host writes it (fastsim on a Mac does): about a fifth of a PNG's bytes, in the same time. A host that cannot falls back to PNG. `--frames png` keeps them exact, for frames two runs are compared by.
- Analytics events are kept with every run that keeps a report (`--out`), not only with `--events`.
- A case can say why it matters (`why`), what is true when it starts (`given`) and the ticket it covers (`ticket`); the report shows them, with `description` and `expected`, above the steps.

## 0.4.0

- `lynkeus headless init` installs what the Node host runs on (jest, `@testing-library/react-native`, `lynkeus-headless`) when the app lacks it, and is served over MCP. `headless start` says what is missing instead of failing inside `npx jest`, and when the app's jest configuration does not set them it passes the React Native preset and the `transformIgnorePatterns` that let React Native, React Navigation, Expo and the like through, so an app with no jest setup of its own runs headless as it is. `status` says whether the app can run headless. A package manager is found by the lockfile above the app too, as in a monorepo.
- `lynkeus mcp` can set a project up and test it, not only drive an app that is already attached. It serves `init` (which now also installs `lynkeus-agent`, with Expo's installer or the project's package manager), `status` (new: what the project has and, for each thing missing, what fixes it), `case init` and `case run`, and tells the model that connects the order to do things in. `LYNKEUS_REPORTS_URL` defaults to `https://lynkeus.io`, so pushing a run needs `LYNKEUS_REPORTS_KEY` alone. `init` adds the Babel plugin to a config written on one line.
- `lynkeus init` makes the project's token and nobody sets a variable for it: it writes a random one to `.lynkeus/token` (kept out of git by `.lynkeus/.gitignore`), and the CLI, `lynkeus mcp`, `lynkeus headless start` and `lynkeus-agent/babel` read it from there. An Expo app gets it as `EXPO_PUBLIC_LYNKEUS_TOKEN` in `.env.local`. `LYNKEUS_TOKEN` in the environment still wins, so nothing changes for a setup that sets it.
- `case run --video-scale <n>` asks the host for a film of that many pixels per point. fastsim films at 2 unless told, and takes 1 to 3: sharper costs time and bytes (one case took 34 s at 3, 22 s at 2 and 21 s at 1; 15 s with no film).
- `case run --screenshots` waits 150 ms of a still screen before each frame, where it waited 700 ms: the wait is paid on every step and was half the time of a filmed run (three cases at once took 133 s, and 68 s without it). `--settle <ms>` sets it; `--settle 700` gives the frames two runs can be compared by, pixel for pixel.
- Setting an app up over MCP, tried on a bare project and on a copy of a React Native app with Redux and styled-components: a failed install says why (the peer range that does not match) instead of where npm keeps its logs; `headless init` makes the project's token too, since `headless start` refuses to run without one and an app tested only headless never runs `init`; `apiUrl` in `lynkeus.config.json` gives the host its local backend when the environment does not, because an agent cannot export a variable; Redux Toolkit, React Redux, Redux, Reselect and Immer are let through jest's transform, as they ship ES modules to React Native; and `case run --host` reports the host's own explanation of a crash, where it cut it off at jest's code frame.
- An Expo Router app runs on the headless host. It has no root component, so `headless init` writes an entry that renders the router over the app's route files with `expo-router/testing-library` and mounts the agent with `auto()`, which then knows the routes. For an Expo app it installs `jest-expo` (with Expo's installer), and `headless start` gives Jest that preset, maps style sheets to an empty module and maps the `tsconfig.json` aliases, the longest first. On React Native 0.86 and later, which moved its Jest preset out of `react-native`, `headless init` installs `@react-native/jest-preset` of the same version. A new Expo SDK 57 app, set up and tested only over MCP, passes a case in under half a second.
- `headless doctor` is served over MCP (`headless_doctor`), so an agent setting up headless sees which native modules still need a mock, and the server's instructions give the headless order of things. It no longer counts a mock or a native module named only in a comment: the generated entry's example `jest.mock('some-native-package', …)` was listed as mocked.
- `lynkeus mcp` exits when its client closes the connection. It used to stay, holding the driver's port, and the next server or `case run` could not bind it.
- `lynkeus-headless` mocks `react-native-vector-icons`' native module, so a screen that renders an icon to an image (`getImageSourceSync`) loads in the Node host instead of failing to render.
- A failed `app.see` with its own `timeoutMs` takes about that long. On an app that says it is native, a text that was not on screen got a last look of 20 s whatever the step asked, so a step of 1.5 s failed after 22 s; the 20 s stay for a step that names no timeout.

## 0.3.0

- `lynkeus-agent`: a token that the app passes and that arrives empty keeps the agent off, with a line in the app's log saying why. It used to mean "no token", and the agent served any driver that connected. In a React Native app that was every app that followed the README, because `process.env.LYNKEUS_TOKEN` is undefined inside a bundle. **An app that passes `token` now needs the value to reach it**: `lynkeus-agent/babel`, a Babel plugin, writes `LYNKEUS_TOKEN` into a development bundle (never a release one), and `lynkeus init` adds it to `babel.config.js`. `auto()` with no `token` at all still serves without one.
- An app that says it runs on Android has its device found through `adb devices`. With an iOS simulator booted beside the emulator, the CLI took the simulator's id for it, and a screenshot, a launch or an `os` command went to `adb` with an id it did not know.
- `wait` and `see` take `route:<name>` for a route that does not start with a capital, as Expo Router's do (`route:index`): a lowercase word alone is still a text to look for.
- `lynkeus init` mounts the agent from the app's entry. In an Expo app it reads the token from `EXPO_PUBLIC_LYNKEUS_TOKEN`, the only kind of variable Expo passes to the app, and an Expo Router app, which has no entry of its own, gets an `index.js` that mounts the agent and then loads the router. Tried on a new Expo SDK 57 project: a development build attaches, lists the screen and names Expo Router's routes; no config plugin is needed.
- A target in quotes is the text inside them: `press '"Next"'` used to look for a label with the quotes in it and find nothing. Quoted, a word is never a route, an index or a testID, so `wait '"Next"'` waits for the button and not for a route called `Next`.
- Cases: `app.press` and any step that takes a `target` take `testId` in its place, `app.press` takes `{ text }`, and `app.type` takes `timeoutMs` for how long its field may take to arrive. Each was refused with `press has no testId`, `app.press needs a target` or `type has no timeoutMs`.
- `lynkeus lint --baseline` knows a finding again by its rule, its testId and what it is about, not by its message. The message carries what was measured, so a target that went from 32 to 30 points came back as new. A baseline saved before this still matches on the message it kept; save it again to get the new behavior.
- `qa.observe` works with a Redux store. It read the new state from the listener's argument, which Zustand passes and Redux does not, so every key of a Redux store was traced as changing to nothing. It now reads the state from the store.
- The store changes in the trace no longer carry a secret or a payload: a key named like one (`token`, `password`, `session`…) is traced as `…`, and a string longer than 80 characters is cut. A trace is part of what a report uploads.
- `lynkeus-agent`: importing the package no longer evaluates the client. `start`, `createHandlers` and `dispatch` were re-exported from the entry, so an app that imported `<Lynkeus>` and left it disabled, as a release build does, still evaluated everything that reads the screen unless Metro inlined its requires. They are now required when called.
- Docs: the protocol's handshake as it is (the driver's `auth` always comes first and carries a `session`; `hello` answers it), how the app paces its dials, the `trace` method, and what was unsaid about physical devices, film and Expo Router on the headless host. Node 22 is the oldest supported everywhere it is named.
- `lynkeus-agent`: an input's `value` is what its native field holds. It was read from React's props, so a field the app does not control (no `value` prop) read as empty after typing, and one with a `defaultValue` went on reading as that. The native module answers `texts(tags)`; an app has to be rebuilt to get it, and until then the agent reads the props as before.
- `lynkeus-agent` on Android: a control is covered only by what a touch would stop at. The agent's own search took any visible view over the point, and React Native lays an invisible debugging overlay over every dev build, so every control read `~covered` and a case waited out its deadline before each press. It now asks React Native's search for a touch's target. An app has to be rebuilt to get it.
- `lynkeus lint` measures the contrast of every text against what is behind it, on the pixels of a screenshot, and reports what falls short of WCAG 2 AA (4.5 to 1, or 3 to 1 for large text) as `low-contrast`. Elements say the size and weight of their text (`font`, optional in the protocol). `lint.contrast` in the config sets the ratios, leaves testIDs out or turns it off; `--no-contrast` skips it once. A host that takes no screenshots says so and reports the rest.
- `lynkeus-agent` on Android: an element is where its view stands, not where the shadow tree puts it. In an app that draws under the status bar the two were a status bar apart, so a press landed above its target. The native module answers `frames(tags)`; an app has to be rebuilt to get it, and until then the agent behaves as before.
- Cases: `on:` takes `has:<command>` (the app registered that command, as a hosted build often does and a store build does not) and `!` in front of any condition, so one case or macro carries the way each host does a thing. `app.press` waits half a second for a target that is not listed and then scrolls to it, instead of spending its whole deadline first, and waits for a disabled control through the app rather than by sleeping, which lets a host with its own clock move on.
- `case run` on a device, or a host that lists only its window: `app.see` and `app.press` scroll to what they look for, and `app.see` gives a missing target a short wait, a scroll and a long wait before its deadline counts. A case no longer needs a swipe written before each element below the fold.
- Fixtures: before the first case lynkeus sends `{"command": "lynkeus.describe"}` to the project's fixtures command. A server that answers `{"commands": [...]}` has its cases checked first, and one that names a fixture missing from the list is refused before anything runs. A server that answers `"ok": false` is left unchecked. `case init`'s server answers it.
- A case step the host cannot do (the app or host answers `Unknown method`) is reported as `unsupported` instead of failed. The case stops there with result `unsupported`, is not retried, and does not fail the run: `3/5 passed, 2 cannot run on this host`.
- `case run --out <dir>` writes the run as a directory: `run.json` (when, on what, totals) and `cases.jsonl` (a line per attempt, each step with its section, outcome and the analytics events it caused). `lynkeus-protocol` exports its types (`RunManifest`, `RunCase`, `RunStep`, `RunEvent`) and `RUN_SCHEMA`, the contract for whatever reads a run.

## 0.2.0

- `lynkeus`: commands regrouped. Static knowledge is `lynkeus map build|screens|show|paths|plan|impact|check|changes` (was `graph`, `screens`, `screen-info`, `paths`, `plan`, `impact`, `check`). What the OS hands the app is `lynkeus os deeplink|appstate|clock|biometrics|scan|gallery|permissions|push|appearance|location|language` (was the bare names and `lynkeus device …`). The host is `lynkeus headless start|init|doctor` (was `headless`, `init`, `doctor`). `lynkeus mock` is unchanged. The old spellings still work as aliases.
- New commands: `see` (assert a route or element is on screen now), `hello` (what the app said about itself), `screen --tree` (the screen as nested lines of meaning, no geometry), `snapshot <name>` (a tree baseline by default; `--pixels` adds the screenshot), `flake` (the same flow n times), `why` (why the last step failed, from the screen, requests and trace), `record` (a flow from what a person does in the app), `lint --save` / `--baseline` (only the findings that are new).
- `lynkeus.config.json` in the app's folder holds what was repeated as flags: `entry`, `apiEnv`, `port`, `device`, `app`, `attachTimeout`, `lintBaseline`. Flags win over the environment, the environment over the file.
- Global flags: `--root`, `--device`, `--app`, `--launch`, `--attach-timeout`, `--json`, `--help`.
- The token env var is `LYNKEUS_TOKEN`. `lynkeus headless start` refuses to run without one.
- Headless respects what a device would refuse: a swipe on an element the platform is not presenting fails; a swipe across a scroller scrolls it (a pager turns its page), and frames follow the scroll. Percentage widths and heights are laid out.
- `screen` lists only what is presented and counts the rest in the header (`--all` lists it), prints coordinates only with `--frames` and read stats only with `--verbose`; states read `!disabled`, `~covered`, `~inert`. About half the tokens per screen; an icon inside a button is not listed. Recorded screens keep only what is presented.
- `lynkeus mcp` serves nine core tools (about 750 tokens a turn, against 4,200 for all of them); `--full` serves all of them.
- Targets can be scoped: `press '#like' --in 'hi from Ana'`, `--nth 2` (protocol: optional `within`). `wait <target> --scroll` swipes until it is in the window; a device press brings an offscreen target in first. `type … --submit` sends the return key.
- Every app answers `events` (what `qa.event` recorded) and `stores` (the state of what `qa.observe` exposed). `run --events` keeps each step's events; `events`, `events diff`, `funnel check` and `funnel report` read them against `.lynkeus/funnels/`.
- `map check` and `map impact` follow a named import through a barrel to the file that defines it: a changed hook reaches the screens that use it, not every screen that imports from the barrel.
- `case run` runs cases written as markdown: `app.*` steps drive the app, any other step is a fixture answered by a command the project declares (JSON lines), `assert` reads the backend, and `cases.macros` names steps of the project's own. `case init` writes an example, the reference and a fixtures server to start from.
- `map ci` writes a workflow that comments on each pull request which screens its diff reaches.
- A command outside a session attaches in about 100 ms (it was 120 ms to 1.8 s): the agent redials every 100 ms for 3 s after a drop, the driver listens before asking the OS for simulators, and the source extractor loads only for `map build`. The crawl returns to where it began instead of a fixed route. `debug` names the component that blocks a touch.
- Linted with Biome in CI; `lynkeus-client` and the protocol's shapes are tested; no product names in the sources, and a test keeps it so.
- Docs split: the README is a landing page; the manual lives in `docs/` (CONCEPTS, DRIVE, HEADLESS, KNOWLEDGE, TROUBLESHOOTING) next to the generated COMMANDS and PROTOCOL.
